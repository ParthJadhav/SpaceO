# SpaceO 1.0.9 release preparation

## Owner decision and scope

On October 16, 2026 the owner asked for a council to investigate the ColorSync issue and fix it.
The fix merged as [#59](https://github.com/ParthJadhav/SpaceO/pull/59) (`20c507d`). The owner was
then told that no release contained it, that the root cleanup on this Mac had not been run, and
that verifying the cleanup before a release was recommended. The owner granted administrator
access on this Mac and instructed: **"do everything which is needed"** and **"do not log out
though"**. This is recorded as GO to apply the cleanup on this Mac and to construct and publish
1.0.9 with the qualification exception below, conditional on passing source, CI, signing,
notarization, immutable-candidate and distribution checks. No missing or failed safety result
is relabeled as passed. The exception applies only to 1.0.9.

The release source is remote `main` at `20c507d` plus this preparation, which changes only
`VERSION`, `SpaceOVersion.current` and documentation. Version 1.0.8 remains available for
rollback.

## Deterministic evidence

The #59 head passed `scripts/test.sh safe` (1,925 Swift tests), the optimized warnings-as-errors
build, the MCP smoke check, the release-security and live-gate shell tests and the public privacy
check on Xcode 27.0 / Swift 6.4 (arm64). Hosted CI passed on pinned Xcode 26.3 / Swift 6.2.
Automated review raised findings on seven consecutive pushes; all were fixed and their threads
resolved, and the final head had none. The cleanup's root path, including partial, unconfirmed
and refused outcomes, is covered against a simulated ColorSync.

## Host cleanup on the development Mac

Apple Silicon MacBook Pro, macOS 27.2 (26B5091g), built-in display only, with the owner's
administrator access. The investigation and the measurements are in the
[identity investigation](2026-10-16-colorsync-display-identities.md#host-cleanup).

- Every SpaceO process was stopped first: four MCP servers and the installed 1.0.7 daemon, with
  no session or display open. The `20c507d` build was installed to `~/.local/bin/spaceo`.
- `sudo spaceo safety clean-display-identities --apply --operator --json` reported
  `ok: true`, 525 registrations unregistered, 0 remaining, 763 profiles removed, none failed,
  verification complete. The backup (764 files, 4.1 MB) is readable only by root.
- The ColorSync registry shrank from 1,211,227 to 4,975 bytes and the profile directory from 767
  to 4 profiles; the physical, built-in and Sidecar profiles were untouched. The read-only listing
  went from 24 seconds to 0.02 seconds.
- In the five minutes before cleanup ColorSync answered 595 display requests (5.0 units) at
  10.7% + 8.0% CPU, about 95 ms per request. In the five minutes after it, with the owner still
  logged in, it answered none and used 0% CPU.

## Live evidence and admission

Normal admission refused the first post-cleanup display creation with
`recent_windowserver_diagnostic`: the 01:13 WindowServer watchdog report was written during the
current boot, and such a report blocks normal admission until the Mac restarts. That refusal is
the designed behavior; the report was not removed or bypassed. The refusal latched the display
safety journal with no display created; after the daemon stopped and only the built-in display
remained, the journal was archived through the documented operator procedure.

Live checks on the exact release source therefore used the testing-host override, which since
#59 keeps the measured ColorSync gate. Results are recorded in the
[identity investigation](2026-10-16-colorsync-display-identities.md#host-cleanup).
